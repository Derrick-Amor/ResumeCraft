## 1 五份文档各管什么（冲突时按此裁决）

这是整套体系能不能跑起来的地基。主 Agent 一旦搞混，后面全是重复劳动。

| 载体 | 管什么 | 不管什么 |
|---|---|---|
| PRD V1.3 | 需求唯一事实源、边界、验收条款、FR 编号 | 不写怎么做、不记录进度 |
| 开发任务分工 V1.2 | 任务卡定义、分派顺序、交付物、验收标准 | 不记录执行状态（状态在 TAPD） |
| 多 Agent 执行规范 V1.1 | 协作机制、角色编制、目录所有权、质量门、红线 | 不重复需求内容 |
| **TAPD 空间** | **执行状态机**：谁在做、做到哪、卡在哪 | **不承载需求和边界**（别在 TAPD 里改需求描述） |
| 工作区 `docs/` | 执行计划包、契约、交接报告、验证记录 | —— |

**冲突裁决顺序：** PRD 边界 > 任务分工定义 > 执行规范机制 > TAPD 状态。
**禁止双向维护：** 需求内容只在文档里改，TAPD 只跟状态。两边都改 = 一定不一致。

## 2 主 Agent 是什么、不是什么

| 是 | 不是 |
|---|---|
| 调度器：拆解、派单、验收、集成 | 不是写业务代码的人（业务代码由子 Agent 写） |
| 质量门执行者：跑命令、看输出、判通过 | 不是需求决策者（范围、优先级由 Amor 定） |
| TAPD 唯一写入者：状态记账、缺陷登记 | 不是唯一写入者之外的第二个人（子 Agent 不许碰 TAPD） |
| 上下文守门人：每张卡只给子 Agent 必要信息 | 不是信息中转站（不替子 Agent 做技术判断） |

**核心矛盾与解法：** 主 Agent 既派单又验收，存在「自己批自己」的风险。
解法是**验收只认机器证据**——命令输出原文、测试结果、文件 diff，不认子 Agent 的自述报告。
这条写进启动指令，是整套体系的防伪机制。

## 4 首次回复验收清单（只用于查启动首轮有没有跑偏）

> **适用范围（2026-10-23 补）：** 本清单是**一次性门禁**，只查主 Agent 启动首轮的五项产出。
> 每张卡的验收仍按 §7 执行（命令级质量门 + 卡级命令 + 对照 FR + 七段式报告），**不得用本清单替代卡级验收**——清单查的是"动作有没有做"，卡级验收查的是"结果对不对"。

| # | 检查项 | 合格标准 | 不合格的表现 |
|---|---|---|---|
| 1 | 读没读文档 | 能准确说出 M0 含 TC-001/TC-002，且引用具体 FR 编号 | 泛泛说"我会按敏捷流程推进" |
| 2 | 有没有写代码 | 五项产出全是文档，没有 src/ 文件 | 直接开始建项目、装依赖 |
| 3 | 目录树 | 与任务分工附录 A 一致（**11 个 src 目录** = 10 个模块 + `src/assets/`）；卡内明确要求的额外目录必须显式标注并列入待确认 | 无标注地发明 `src/editor/`、`src/pages/` 等未声明目录 |
| 4 | 契约草案 | 只写 TS 接口，P1 部分明确标注"骨架"且不列端点 | 编造 HTTP 端点、写 Swagger |
| 5 | 阻塞问题 | 不超过 5 条，都是真需要 Amor 拍板的 | 列了 15 条琐碎问题，或一条没有（说明没细读） |
| 6 | 有没有在确认前建条目 | 计划包确认前 TAPD 只读不写；已获准的归档与建卡须在**同一操作窗口**完成 | 一上来就批量建了迭代或 18 条需求 |
| 7 | 顺序与依赖 | 前 3 卡顺序能在任务分工依赖图上走通；与文档罗列顺序不同处给了理由 | 顺序违反前置依赖（如先派 TC-008 后派 TC-007），或无理由打乱 |
| 8 | 范围零漂移 | 每处新增约束标注"不改变 PRD 范围"；每处删减已报备 | 私自加功能/加技术栈、私自砍掉 MVP 范围（如导入能力） |

**发现跑偏就直说**：「第 X 项不符合，原因是 Y，重做这一项，其余保留。」

**版本说明（2026-10-23 v1.1）：** 原 6 项中，第 3 项与任务分工附录 A 自相矛盾（附录 A 漏列 TC-006 要求的 `src/assets/`），第 6 项与附录 A 归档闸门时序表述冲突；本次一并修正，并补第 7、8 项（原清单只查动作、不查结果，容易激励表演）。

## 5 TAPD 生命周期管理协议

### 5.1 对象映射（本项目专用）

| TAPD 对象 | 对应什么 | 用量 |
|---|---|---|
| 迭代 Iteration | 里程碑 M0–M5 | 6 个，一次只开 1 个 |
| 需求 Story | 任务卡 TC-XXX | 18 条（17 条 MVP + TC-014 后置），平铺不建父子 |
| 缺陷 Bug | 验收不通过项 | 按需，挂在对应需求下 |
| 测试用例 TCase | 卡级验收命令 | M3 阶段（TC-013）批量建，之前不建 |
| 任务 Task | **不使用** | 一张卡已是原子单元，再拆只是重复劳动 |
| 发布 Release | MVP 上线 | 只建 1 个，M5 时 |
| Wiki | 架构决策归档 | **MVP 阶段不使用**（决策均在基线文档）；P1 后端启动时再建 |

**为什么不建父子需求：** 18 条平铺足够看清全貌，建父子反而要多点一层才能看到卡。
模块归属靠标题前缀解决，如 `TC-006 布局引擎·测量与单位`，不依赖 TAPD 的模块字段配置。

### 5.2 状态映射

| 卡状态（任务分工） | TAPD 需求状态 | 补充动作 |
|---|---|---|
| 未开始 | 规划中 planning | —— |
| 进行中 | 开发中 developing | 评论记录：派给谁、开始日期 |
| 待验收 | **产品体验 status_2** | 评论贴交付报告路径 |
| 已完成 | 已实现 resolved | 先转 status_3 中转，再转 resolved；评论贴验收命令输出结论 |
| 阻塞 | 保持原状态 | 加「阻塞」标签 + 评论写卡点与解除条件 |

**流转链路（实测工作流，2026-10-23 用 get_workflows_all_transitions 核对，不得凭印象操作）：**
```
规划中 planning → 开发中 developing → 产品体验 status_2 → 测试中 status_3 → 已实现 resolved
```

- **`developing` 不能直达 `status_3`**：`developing` 的可达目标只有 `planning` / `developing` / `status_2`。直接转「测试中」会失败。
- **`status_3` 是技术中转态，不停留**：验收通过时连续执行 `→ status_3 → resolved` 两步，中间不写评论。
- **转「开发中」时 `owner` 字段必填**（工作流 Appendfield 校验 `Notnull=yes`）：派卡时统一填 `郭涛`，不填则流转失败。
- 每次流转前先调 `get_workflows_all_transitions` 复核当前状态的可行目标；目标不可达时按上述链路补中转，不要反复试错。
- 「已拒绝」仅用于需求作废，**不用于删除**——删除会丢决策痕迹。

### 5.3 六个记账触点（主 Agent 必须做，缺一即失控）

| 时机 | TAPD 动作 | 证据要求 |
|---|---|---|
| 项目启动（一次性） | 归档示例数据 → 建 6 个迭代 → 建 18 条需求并挂迭代 | 建完回读一次，确认 18 条都在 |
| 派卡前 | 需求转「开发中」（`owner` 必填：郭涛）+ 评论写派单摘要 | 派单六项写全 |
| 子 Agent 交付 | 需求转「产品体验 status_2」+ 评论贴 `docs/handoff/TC-XXX.md` 路径 | 报告七段式齐全 |
| 验收通过 | 需求转「已实现」（`status_2 → status_3 → resolved` 两步）+ 评论贴质量门命令与输出摘要 | 有真实命令输出 |
| 验收不通过 | 建缺陷挂回需求 + 需求保持「产品体验 status_2」 | 缺陷描述含失败现象与复现路径 |
| 里程碑结束 | 关闭迭代 + 输出阶段报告 + 更新 TASKS.md | 阶段报告含变更摘要/验证结果/下阶段建议 |

### 5.4 迭代日期怎么定

**本项目口径（2026-10-23 Amor 决策）：只排工期，不设截止日期。** 理由是它是个人变现开发项目、与毕设排期无关，且 AI 辅助下可能提前完成——设死截止只会制造假逾期。

- 建迭代时填**估算窗口**（依据 `docs/plan/PLAN.md` 的工期表），并在迭代描述注明"估算锚点，随实际滚动更新"。
- 实际用时记入 PLAN.md 的「实际」列；偏差超过估算 30% 时，主 Agent 同步更新 PLAN.md 与 TAPD 迭代起止日期。
- **仍然禁止：** 编造硬截止日期、把估算当承诺对外宣称、因为"反正是估算"就随手填当天日期。

### 5.5 记账纪律（防 TAPD 变成垃圾场）

1. **一条需求只对应一张卡**，卡号进标题，正文不重复 PRD 内容。
2. **状态变更必须带评论**，说清为什么转。没有评论的状态变更视为无效操作。
3. **不删需求**。需求作废就转「已拒绝」并加评论说明原因，删除会丢决策痕迹。
4. **不在 TAPD 里讨论技术方案**。讨论放交接报告或 Wiki，TAPD 只留结论一行。
5. **每个里程碑结束做一次对账**：TAPD 状态 = TASKS.md 状态 = 实际代码。三者不一致先查清再继续。

### 5.6 降级方案（TAPD 工具不可用时）

主 Agent 若调不到 TAPD 工具：
1. 立即告知 Amor「TAPD 未连接，降级为本地记账」
2. 在 `docs/plan/TASKS.md` 维护完整状态
3. 每个里程碑结束输出一份「TAPD 同步清单」（卡号 + 目标状态 + 评论内容），由 Amor 交给阿U 批量执行

**绝不允许：** 假装写成功、跳过记账继续开发。状态失真比不记录更危险。

### 5.7 打回、缺陷、幂等与补录细则（P1 条款，主 Agent 必须执行）

**① 需求描述四要素（建需求时固定格式，不抄验收条款原文）**
```
目标：〈一句话，≤50 字〉
FR：〈FR 编号映射〉
依据：《开发任务分工》第 X 节 TC-XXX（含可写目录，见附录 F.1）
验收：pnpm verify:xxx（或卡级命令）
```
不放验收条款原文——原文会随文档升版漂移，双向维护必然不一致；用指针引用。

**② 打回评论格式（验收不通过时）**
```
【打回 第N次/共2次】失败现象：……｜复现路径：……｜涉及文件：……
```
需求保持「产品体验 status_2」不变，不转回「开发中」——避免状态抖动，修改进展写在缺陷评论里。

**③ 缺陷生命周期**
- 缺陷不分级（单人项目够用），或简单两档：阻塞 / 非阻塞。
- 关闭条件 = 原卡级验收命令重跑通过 + 主 Agent 评论「【缺陷关闭】命令输出原文摘要」。
- 未关闭缺陷数 > 3 时，暂停派新卡，先清缺陷（报 Amor）。

**④ 幂等规则（防重复写入）**
- 所有 TAPD 写操作前先回读当前状态。
- 批量建需求后，按「TC-XXX 标题」去重核对，不按数量核对。
- 重复内容不重复发评论；评论带时间戳。

**⑤ 连接失效的重试与补录**
- 失败立即重试 1 次 → 仍失败：降级（TASKS.md 升主账）+ 在 `docs/plan/TAPD-SYNC.md` 记待同步清单（卡号 + 目标状态 + 评论内容）。
- 恢复后按清单补录 → 回读校验 → 评论告知 Amor「已补录 N 条」。

**⑥ Amor 手动变更的处理**
- 主 Agent 发现非本 Agent 造成的 TAPD 变更（Amor 从网页端改的），先评论 @Amor 确认，不强行覆盖。

**⑦ TASKS.md 同步频率**
- TASKS.md 常态维护：每卡闭环即更新（TAPD 正常时它是镜像；TAPD 降级时它升主账）。
- 里程碑结束三方对账：TAPD 状态 = TASKS.md = git 实际代码，不一致先查清再继续。

**两道闸门（顺序不能反）：**

1. **计划包闸门：** 第 2-6 步（归档 → 建迭代 → 建需求 → 回读）必须等 Amor 确认执行计划包之后才做。归档虽然只是软删除、可恢复，但也**并入同一操作窗口**一次做完，不再"接管后立即做"——两次改状态会让看板出现中间态，且多一轮状态核对（2026-10-23 裁决，与 §4 清单第 6 项判据一致）。
2. **日期闸门：** 计划包没确认就建需求，等于把没定稿的东西写进系统；迭代日期按 §5.4 口径填估算窗口，不得编造硬截止日期。

**一次做完的顺序：** 归档示例数据 → 回读确认 16 条需求已到 `end`、4 个迭代已关 → 建 6 个迭代（填估算窗口）→ 建 18 条需求并挂迭代 → 回读按「TC-XXX 标题」去重核对 → 向 Amor 报数。
