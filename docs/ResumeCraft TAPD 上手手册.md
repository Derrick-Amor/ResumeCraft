> 编写日期：2026-10-23

## 一、心智模型：六个对象各回答一个问题

| 对象 | 回答的问题 | 你的对应物 |
|---|---|---|
| 需求 Story | 做什么、为什么做 | PRD 的 FR-XXX |
| 任务 Task | 具体怎么实现 | **本项目不使用**（一张卡 = 一条需求，见 §二） |
| 迭代 Iteration | 什么时候做完 | 里程碑 M0–M5 |
| 测试用例 TCase | 怎么算做对了 | 需求的验收标准 |
| 缺陷 Bug | 哪里没做对 | 验收不通过项 |
| 发布 Release | 什么时候给用户 | 版本上线节点（MVP 前可不用） |

**关系一句话：** 需求是锚点，其余五个都挂在它身上。

```
需求说做什么 → 任务说怎么做 → 迭代说什么时候做完
                    ↓
              用例说怎么算做对 → 缺陷说哪里没做对 → 发布说何时交付
```

**最容易搞混的一点：**

- 需求是「用户要什么」——不可再拆的业务价值单元
- 任务是「我要做几步」——可以拆到 2 小时粒度的执行单元

写成「写布局引擎代码」是任务；写成「内容超出页面时能检测并提示」才是需求。
混了就没法验收，因为任务天生不可验收。

## 二、开发过程五阶段与 TAPD 的映射

| 阶段 | TAPD 载体 | 你该在这里做什么 |
|---|---|---|
| 需求分析 | 需求 Story | 把 PRD 的 P0 条目落成需求，写清验收标准 |
| 方案设计 | 基线文档 | 架构决策与选型理由都在 PRD 与《后端架构决策汇总》里；**MVP 阶段不建 Wiki**（P1 后端启动再建，见主控规范 §5.1） |
| 编码实现 | 需求（状态流转） | **Task 层不使用**；一张卡 = 一条需求，派单即转「开发中」（依据：主控规范 §5.1） |
| 测试验收 | 测试用例 + 缺陷 | 用例是「通过条件」，缺陷是「没通过的证据」 |
| 发布上线 | 发布计划 + 迭代关闭 | MVP 前可跳过，用迭代关闭代替 |

## 三、日常节奏：TAPD 的唯一实际用处

> 让你每天早上不用想「今天做什么」。

| 时机 | 动作 | 判断依据 |
|---|---|---|
| 早上开工 | 打开迭代看板，挑一张卡拖进「开发中」 | 只挑一张，不多挑 |
| 做完一张 | 逐条跑验收标准 | 全过才转「已实现」，有一条不过就提缺陷 |
| 每周收工 | 看这周关了几张、没关的为什么 | 连续两周关不掉 → 卡太大，拆掉 |

**单人开发不需要的功能：** 工时统计、甘特图、燃尽图、多人权限、Sprint 评审会。
功能表很长，别被吓到。用不上就是用不上。

## 四、你的项目映射表

| 你的文档 | 放进 TAPD 的哪里 | 例子 |
|---|---|---|
| PRD 的 FR-XXX | 需求描述里带 FR 编号（标题用 TC-XXX，见下一行） | `TC-005 需求描述含 FR-CMP-001~004` |
| 任务分工的 TC-XXX | 需求（一张卡一条，不拆 Task） | `TC-005 简历组件集（中英双轨）` |
| 里程碑 M0–M5 | 迭代 | `M1 编辑器地基` |
| 验收不通过 | 缺陷，挂回对应需求 | `FR-EXP-005 中文导出字体缺失` |
| 边界声明（不做什么） | 需求描述的「不做」段 | 防止 Agent 越界扩需求 |

**推荐粒度：** 一张任务卡 = 一条需求。贴合「一次一卡、逐卡验收」的节奏，数量可控。

**为什么不按 FR 建：** FR 数量到 40+ 条，管理成本高于收益，且很多 FR 在 MVP 阶段不会动。
**为什么不只建模块：** 模块级需求太粗，无法验收，等于换了个地方写愿望。

## 五、怎么写验收标准（核心技能）

判断写没写对，用三个条件：

| 条件 | 反面例子 | 正面例子 |
|---|---|---|
| **可观察** | 性能良好 | 导出 2 页简历耗时 < 3 秒 |
| **有阈值** | 支持中文 | 宋体 11pt 中文导出 PDF 无方框、无缺字 |
| **有反例** | （没写失败条件） | 出现任一缺字或错位即判失败 |

达不到这三条的，不是验收标准，是愿望。

**为什么这条最重要：** 多 Agent 开发中，验收标准是唯一能防止「Agent 说自己做完了但其实没做」的机制。
写得含糊，就只能靠人肉复查，等于没上管理工具。

## 六、三个坑

1. **把任务当需求用。**
   需求不可验收，整个追踪链就断了。三个月后你只知道「写过代码」，不知道「做成了什么」。

2. **同时开好几个迭代。**
   未关闭的迭代超过 2 个，等于没有迭代。单人项目一次只开一个。

3. **只记录不回头。**
   TAPD 的价值不在今天看着整齐，在三个月后能查清「这行为什么这么写」。
   所以每个需求必须留一条能追溯的线索——FR 编号。

## 七、AI 能帮什么、不能帮什么

| 层面 | 能力 | 说明 |
|---|---|---|
| 批量建条目 | ✅ | 一条指令生成几十条需求 / 任务 / 缺陷 / 迭代 |
| 盘点进度 | ✅ | 按迭代、状态、负责人拉清单，直接出周报 |
| 转状态 | ✅ | 但必须遵守工作流规则，不能跳级 |
| 挂关联 | ✅ | 缺陷挂需求、任务挂需求、子需求挂父需求 |
| 写 Wiki | ✅ 有能力，但 MVP 不建 | 直接写 Markdown；本项目决策都在基线文档，P1 再建 |
| 定时巡检 | ⚠️ | 需另配自动化任务 |
| 改空间配置 | ❌ | 自定义字段、工作流、成员权限、看板视图，接口未开放 |
| 判断质量 | ❌ | 这张卡算不算通过，只有验收标准说了算 |
| 决定范围 | ❌ | 砍不砍需求、先做哪个，只有人能定 |

**结论：** AI 是记账员 + 巡检员 + 报表员，不是项目经理。
项目经理那部分（判断、取舍、担责）不可替代。

## 八、第一步：最小起步

三件事做完就能跑：

1. **归档示例数据**
   当前空间有 16 条【示例】需求（校园小拍卖家 / 买家应用）+ 4 个示例迭代，
   是建空间时套用电商模板带入的，与本项目无关。归档即可，TAPD 的删除是软删除，可恢复。
   **时机**：主控接管后立即可做（纯清理动作）；建迭代与建需求必须等 Amor 确认执行计划包之后。

2. **建 6 个迭代，但只开 M0**
   `M0 项目启动`～`M5 打磨与发布`一次建全（轻量操作），**只有 M0 处于开启状态**，其余保持未开。
   日期必须写死且经 Amor 确认，否则迭代没有约束力。

3. **18 条需求一次建全（17 条 MVP 卡 + TC-014 后置卡）**
   与 6 个里程碑一一对应（M0: TC-001/002 ｜ M1: TC-016/003/004 ｜ M2: TC-005/006/017/007 ｜
   M3: TC-013a/008/009/010/011 ｜ M4: TC-012/013 ｜ M5: TC-015），每条带卡级验收命令。
   TC-014 是 P1 后置卡，**建但不挂迭代**，状态留「规划中」并在评论注明「P1 后置」。
   建完回读，按「TC-XXX 标题」去重核对。

**为什么是"建全但只开一个"，而不是"只建几条"：** 需求列表的长度不等于项目管理的质量，
但只录 5-8 条会让看板看不出全貌，且每补一批就要重复一次"建卡 + 回读"。
克制靠两个机制实现——**一次只开一个迭代**（未关闭迭代超过 1 个等于没有迭代）、
**一张卡一条需求**（18 条平铺，不建父子、不拆 Task）。
条目都在但每张都闭环，不是需求墓地；条目少却长期不动，才是。

## 九、状态流参考

当前空间的需求状态流（TAPD 默认，可直接用）：

```
规划中 planning → 开发中 developing → 产品体验 status_2 → 测试中 status_3 → 已实现 resolved
                                                                        ↘ 已拒绝 rejected
```

**两条实测约束（2026-10-23 核对工作流，别凭直觉操作）：**

1. **`开发中` 不能直接跳到 `测试中`**，必须经 `产品体验 status_2` 中转，否则流转失败。
   `测试中 status_3` 只是通往「已实现」的技术中转站，不停留。
2. **转「开发中」时处理人 `owner` 必填**，不填就转不过去。

任务状态只有三个：未开始 (open) / 进行中 (progressing) / 已完成 (done)，本项目不使用任务层。

**注意：** 状态不能跳级。流转前必须先查当前状态可流转的目标状态。

## 十、常见问题

**Q：TAPD 里的东西和我的 Markdown 文档重复了吗？**
A：不重复。Markdown 文档是「事实源」，定义边界和细节；TAPD 是「执行状态机」，记录进度和归属。
冲突时以文档为准，TAPD 只反映状态。

**Q：我可以只用看板不用迭代吗？**
A：可以，但会失去时间约束。看板解决「做什么」，迭代解决「什么时候必须做完」，后者才是防拖延的机制。

**Q：多 Agent 开发时，Agent 能在 TAPD 里操作吗？**
A：能，但建议由主控 Agent 统一操作，避免多个 Agent 同时改同一张卡造成状态混乱。
子 Agent 只回报结果，不直接写 TAPD。

**Q：需求变了怎么办？**
A：不删旧需求，改描述并加评论说明变更原因。删除会丢失决策痕迹，而决策痕迹正是 TAPD 唯一不可替代的价值。

## 附录：本手册适用边界

- 适用于单人 + 多 Agent 的轻量研发场景
- 不适用于多人 Scrum 团队（那需要完整的需求评审、Sprint 计划会、站会机制）
- 迭代长度、需求粒度等参数可按实际节奏调整，但「一次只开一个迭代」不建议破例
