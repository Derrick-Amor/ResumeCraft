# 上篇：主控上下文容量问题

## 1. 接近上限时的表现与判断依据

### 1.1 具体表现（按出现频率排序）

| # | 表现 | 本项目中的典型场景 |
|---|---|---|
| 1 | 遗忘早期约定 | 又问一遍「包管理器用 pnpm 还是 npm」「仓库地址是什么」——而这些在启动指令里写过 |
| 2 | 重复提问 | 同一个阻塞问题 Amor 已答过，主控再次发问 |
| 3 | 参数错乱 | 命令写错路径（`docs/handoff/` 写成 `docs/reports/`）、卡号张冠李戴（TC-008 的事安到 TC-007） |
| 4 | 自相矛盾 | 前半段说「严格一次一卡」，后半段同时派两张 |
| 5 | 验证行为退化 | 不跑命令直接判「通过」、七段式报告缺段也不打回 |
| 6 | 回答变短变泛 | 从「逐条核对 FR」退化成「整体符合预期」 |
| 7 | 把已完成当未完成 | 重复派已验收的卡，或重复建 TAPD 需求 |

### 1.2 可操作的判断依据（三条，任一命中即按「将满」处理）

1. **行为信号**：连续 2 轮出现上表第 1/2/5 类表现 → 立即触发快照，不等系统提示。
2. **节律信号**：每完成 1 张卡（或每约 10 轮对话）自检一次。本项目 18 张卡 × 每卡 4-6 轮，一个会话撑 4-6 张卡就会到高位——**建议每 2-3 张卡做一次快照**。
3. **自报信号**：主控主动报告「上下文占用偏高」。TAPD 规范 §9 已要求「上下文快满了主动输出快照」，但缺触发标准与模板（见下篇 E4）——本次已补齐（见 §4）。

## 2. 缓解方案对比

| 方案 | 适用场景 | 实施步骤 | 代价 |
|---|---|---|---|
| A. 状态外置快照（PROGRESS.md） | **主力方案**，所有阶段 | 每卡闭环/出现遗忘信号时，按 §4 模板写 `docs/plan/PROGRESS.md` | 极低（一次写文件 <1 分钟）；快照本身占上下文可忽略 |
| B. 会话按里程碑拆分 | 里程碑边界（M0→M1 等） | 新会话用 §4.3 恢复指令开场，只带 PROGRESS + 当里程碑相关章节 | 中：切换时有 3-5 分钟核对成本；好处是每个会话天然轻载 |
| C. 上下文摘要压缩（系统自动 compact） | 单会话内的被动兜底 | 无需操作，系统触发 | 摘要丢细节不可控；**不能替代 A**（摘要可能漏掉未落盘决策） |
| D. 资料库归档（决策/报告入资料库） | 跨会话长期留存 | 里程碑报告 + 七段式 handoff 归档进资料库「简历项目开发」文件夹 | 低；注意资料库是留存不是实时状态，检索有成本 |
| E. 定期归档（handoff + 里程碑报告） | 已内含在现行规范 | 每卡 handoff/TC-XXX.md；里程碑阶段报告 | 已被一次一卡机制强制，无新增成本 |

**推荐组合：A 为常态（每 2-3 卡一次）+ B 为节奏（每里程碑一次）+ C/D/E 兜底。**
理由：本项目主控定位是「无状态调度器」，一切状态外置是既有设计（五载体分工），快照机制只是把已有设计补上触发标准。

## 3. 重开对话的代价边界

### 3.1 会丢失的（未落盘的一切）

- 对话中口头确认但没写进任何文档的决策（Amor 说「这个角标用红色#E34D59」而没记入 token 表）
- 当前卡改到一半、未 commit 的文件进度（git status 里的未提交改动若被丢弃）
- 主控对某个模块的「实现思路讨论」中间态（未写进 handoff 第五段「与 PRD 不一致处」或第六段「下一步建议」的）
- TAPD 里没写的临时备注（TAPD 未同步清单）

### 3.2 可保留的（已落盘的一切）

- 五份基线文档 + 两份 TAPD 文档（Obsidian 库 + 工作区 docs/ 双副本）
- git 仓库已提交代码与分支（远程 github.com/Derrick-Amor/ResumeCraft.git）
- TAPD 空间全部状态（需求/缺陷/评论/迭代）
- `docs/plan/PROGRESS.md` 进度快照
- `docs/handoff/TC-XXX.md` 每卡交接报告

### 3.3 一句话结论

**重开对话对本项目零实质影响——前提是执行「决策不落盘不算数」纪律。** 现行规范的五载体设计本来就是按「主控可随时替换」做的，缺口只有一个：PROGRESS.md 没有模板（本次补齐）。
